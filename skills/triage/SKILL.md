# Triage

Move incoming tracker requests through category and state roles. Generated implementation tickets normally enter through /to-tickets; use triage for raw reports and external PRs.

Every tracker comment posted during triage starts with:

    > *This was generated by AI during triage.*

## References

- Read [AGENT-BRIEF.md](AGENT-BRIEF.md) before writing a candidate brief.
- Read [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) before recording a rejected enhancement.
- Use /ticket-readiness for the executable-ticket contract.
- Hand off every ready-for-agent or ready-for-human transition to user-invoked /skill:admit-ticket.

## Roles

Categories:

- bug — existing behavior is broken;
- enhancement — new behavior or an improvement.

States:

- needs-triage — maintainer evaluation is in progress;
- needs-info — exact missing information or decisions are outstanding;
- ready-for-agent — admission returned READY/AGENT and a human confirmed activation;
- ready-for-human — admission returned READY/HUMAN and a human confirmed activation;
- wontfix — the request will not be actioned.

Every triaged item carries one category and one state. Resolve conflicting state labels with the maintainer before further mutation. Read the configured label mapping from docs/agents/triage-labels.md.

## Show attention queue

When asked what needs attention, list oldest first:

1. unlabeled incoming issues;
2. needs-triage issues;
3. needs-info issues with reporter activity after the latest triage note.

When the tracker configuration enables external PRs as a request surface, include only external PRs in discovery and mark every result as issue or PR. An explicitly named PR is always in scope.

## Triage one item

### 1. Gather

Read the full issue or PR, comments, labels, author, dates, linked decisions, and prior triage notes. For a PR, read the exact diff.

Explore the codebase using its domain glossary and ADRs. Perform two searches:

- **Redundancy:** find existing behavior by domain concept, and report where you looked.
- **Prior rejection:** inspect .out-of-scope for a matching decision.

### 2. Recommend

Recommend one category and one next state with evidence. Present the relevant current code path, redundancy result, and prior rejection. Wait for maintainer direction before tracker writes.

### 3. Verify

Verify the request before shaping implementation work:

- reproduce a bug from a tight feedback loop;
- verify an enhancement against current behavior and constraints;
- for a PR, inspect the diff and run the relevant read-only checks.

Report confirmed, failed, or insufficient detail. Insufficient detail normally leads to needs-info.

### 4. Resolve decisions

When behavior or terminology remains undecided, use /grilling and /domain-modeling. Update the domain glossary and ADRs as decisions land. Preserve all resolved facts in triage notes.

### 5. Apply the chosen path

- **Candidate for a ready label:** write or update the Agent Brief, keep needs-triage, print the exact `/skill:admit-ticket <issue identity>` command, and stop. Admission alone applies the label selected by its reviewed execution lane after confirmation.
- **Too broad:** keep needs-triage and propose /to-tickets with the issue as parent/source.
- **needs-info:** post exact established facts and outstanding questions, then apply needs-info.
- **wontfix, already implemented:** point to the implementation and close without adding an out-of-scope record.
- **wontfix bug:** explain the rejection and close.
- **wontfix enhancement:** record the decision in .out-of-scope, link it, and close.
- **needs-triage:** preserve partial findings and keep the state.

## Direct activation requests

When a maintainer asks to move an item directly to ready-for-agent or ready-for-human, prepare the candidate brief if it is missing, keep needs-triage, print the exact `/skill:admit-ticket <issue identity>` command, and stop. The direct request does not bypass the user-invoked fresh review and its later mutation confirmation.

## Needs-info comment

    ## Triage Notes

    **What we have established:**
    - fact with evidence

    **What is still needed:**
    - specific question and decision owner

Do not re-ask questions already answered in prior notes. For a candidate, triage completes when its category, needs-triage state, durable brief, and exact Admission handoff agree; activation completes only in /skill:admit-ticket.
